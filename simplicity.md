# Simplicity Rules Against `anarch-lint`

This document maps every rule of six distilled rulesets to what anarch-lint can
measure deterministically in a Go module:

The rulesets live under [`rules/`](rules). Each rule number links to its rule with a
[text fragment](https://wicg.github.io/scroll-to-text-fragment/), `#:~:text=§N.N,-[LEVEL]`,
whose suffix keeps the match on the rule's own line.

## Verdicts

| Verdict | Count | Meaning                                                                                                  |
| ------- | ----- | -------------------------------------------------------------------------------------------------------- |
| ✅      | 7     | Measurable: a deterministic, gateable check covers what the rule says about Go code                      |
| ◐       | 66    | Partial or approximate: a proxy, a subset of the violations, or candidates that gate only once confirmed |
| ⊘       | 6     | About the checker: the rule says what not to flag, so compliance is a configuration of anarch-lint       |
| ✗       | 101   | Not measurable: method, process, semantics, comparison of designs, or comments and naming                |

Four conditions hold for every ✅ and ◐:

1. **Go only.** The rules are language-agnostic, with examples in Ruby, Java
   and Clojure; anarch-lint measures Go modules. Rules about inheritance,
   `each` or `final` have no Go counterpart.
2. **Deterministic once modelled.** Most checks need `anarch.json` to say which
   packages are the core and which the shell, or which libraries are ORMs or
   actor frameworks. That mapping is a judgement made once; the measure is then
   deterministic. Cite the rule's § in each entry's `reason`, so the report's
   compliance, `gates.minCompliance` and `check --new-from-rev` score and
   ratchet the rules one by one.
3. **Candidates are not verdicts.** Many ◐ signals are connascence or balance
   *candidates*. The list of candidates is deterministic; most gate only after
   a human approves the judgement slot, and some, such as `low-cohesion`, never
   gate.
4. **Some signals need more input.** `hidden-coupling` and the co-change
   measures need `balance --since-rev`; `untested-dependency` and
   `untested-crossing` need `--coverprofile`; `coChange` and
   `fitness.boundaries` rules are checked only by `check --new-from-rev`.
   `invariant-untested` comes only from `fitness --coverprofile`, so `check`
   never gates it.

## Addendum: Missing Context for the Open Conflicts

Conflicts 1, 2, 3, 7 and 8 stay open after reading the sources. Each comes
from something the sources leave out: a definition, an assumption about the
language, or a case the author never considers. For each, this addendum names
what is missing and what it would take to decide.

### 1. Counting Components

**What is missing: a definition of simplicity.** Atwood's post is a
three-minute opinion piece and defines none; its ruleset's Limitations say so.
It quotes fragments of Gabriel's essay but not Gabriel's own criteria.

**What the examples show.** Every one of Atwood's examples removes something
that need not exist: inheritance where a plain object or an interface will do,
a registry where a text file will do, code you write where code you can reuse
exists. Hickey's "more things" comes from the opposite move, separating parts
that are tangled together. Neither author discusses the other move: Hickey
never addresses deleting parts the requirements do not need, and Atwood never
addresses splitting a part that does two things.

**What would decide it.** Read WIB 1.1 as "remove what the requirements do not
need" and SME 1.5 and SM 1.6 as "do not merge independent parts to lower the
count". The two rules then cover different moves and both hold. Under that
reading, `analyze` counts between candidate branches are evidence for WIB 1.1
only when someone has judged the extra parts unneeded. The reading is a choice
this document makes, not one the sources make, so the fix belongs in the
wording of WIB 1.1.

### 2. Maps Against Named Structs

**What is missing: the language.** Hickey's advice assumes a language with
"idiomatic support" for maps: literals, accessors, symbolic keys and generic
manipulation (`SimplicityMatters.md:882-902`). He was speaking to Clojure and
Ruby audiences. He also assumes values are immutable and collections
persistent (`SimpleMadeEasy.md:334`). Go's maps meet neither assumption:

- A `map[string]any` gives up static types and has no symbolic keys.
- A map is mutable, and so is everything shared through it.
- Go reaches a struct's fields generically only through `reflect` or an
  encoding such as `encoding/json`.

Ousterhout's examples are Java and C++, where the alternative to a named type
is `Pair`, whose element names say nothing.

**What neither author considers.** A struct with exported, documented fields
and no methods is Go's usual record. It meets PSD 13.1 and the wording of
SM 4.1, which targets information-specific accessors and methods. It breaches
SME 3.2, which asks for no new named type per piece of information.

**What else is missing: the other 10%.** Hickey's "90% of the time"
(`SimplicityMatters.md:931`) leaves room for named types and never says when.

**What would decide it.** A choice that SME 3.2 does not carry over to Go.
With that choice, one scoring covers all three rules and the `domains` rule:

- A struct with exported fields and no methods complies.
- Getters, setters and other information-specific methods breach SME 3.1 and
  SM 4.1. anarch-lint has no detector for them.
- `Pair`-like generic containers breach PSD 13.1 and Hickey's objection to
  product types alike.

### 3. Encapsulation Against `invariant-exposed`

**What is missing: invariants and mutation.** Hickey's "information" is facts
such as a name and an address (`SimplicityMatters.md:936`). His values are
immutable, so exposing their representation exposes nothing that anyone can
break. Neither talk considers information that must stay consistent as it
changes. His only remedy for rules about data is a declarative rule system
kept apart from the data (`SimpleMadeEasy.md:362`, `:424-426`), an area he
calls "more cutting edge" (`SimpleMadeEasy.md:328`).

**Why Go changes the question.** In Go any package can write an exported
field. Exposing the representation therefore also hands out mutation, and
that is what `invariant-exposed` guards against. Hickey's case against
mutable state (`SimpleMadeEasy.md:286-290`) suggests he would not defend a
field any package can change, but he never says so.

**What would decide it.** One of two scopings, both outside the text:

- **By type.** Score SME 3.1 and SM 4.2 only on types that no modelith
  invariant governs. For a governed type, the invariant is the
  "implementation" that, by Hickey's own test, information lacks.
- **By evidence.** Count as a breach only an exposed entity whose evidence
  lists writes from other packages; both readings condemn those. An exported
  field that nothing outside the package writes is exposure Hickey would
  accept. anarch-lint reports the exported field either way, so this scoring
  reads the finding's evidence, not its gate.

### 7. Implementation Against Interface Simplicity

**What is missing: where Gabriel's tradeoff stops.** Atwood's post never says;
its ruleset's Limitations note the clash with deep-module advice. The post
quotes only the PC-losering story, in which the caller's fix is "this extra
test and loop" (`atwood_worse_is_better.md:16`). Gabriel's own criteria are
not in the source.

**What Ousterhout supplies.** A reason with no number: "Most modules have more
users than developers" (`psd_book.md:1942`), so a cost pushed to callers is
paid once per caller. He also limits his side: expose a failure when callers
need the information (`psd_book.md:3078-3090`). Gabriel's retry assumes the
caller can always simply retry. Neither author says how many callers tip the
balance.

**What would decide it.** Two facts about each routine, both outside the text:

- How many callers it has.
- Whether those callers need to know that the operation failed.

A few callers who need to know favour WIB 2.1. Many callers who would all
write the same retry loop favour PSD 9.3. anarch-lint records call sites but
no check counts callers this way.

**How it affects scoring today.** `timing.no-retry` fires only for outbound
calls in packages that import no resilience library
(`internal/connascence/resilience.go`). It is a low-confidence candidate that
never gates. Where a module follows WIB 2.1 on purpose, reject the candidate
in its judgement slot and cite WIB 2.1 as the reason.

### 8. How Many Components

**What is missing: a threshold.** Ousterhout gives no number for "deep",
so depth is always a comparison between designs; the PSD ruleset's
Limitations say so. Hickey gives no size for "smaller".

**What each author is answering.** Hickey's "many more subcomponents" is
addressed to designs where "usually you have none", and to farming out policy
(`SimpleMadeEasy.md:406`). Ousterhout's classitis targets classes that "don't
contribute much functionality" (`psd_book.md:1003`), each with its own
interface. A part that is independent and deep satisfies both. The open case
is a small, independent part with little behind its interface: Hickey would
keep it and Ousterhout would merge it.

**What would decide it.** Score depth, not count. PSD 3.1's proxy, relative
visibility, is the only measure anarch-lint has, and it does not see depth
directly. Do not score SME 5.3 or SM 5.4 as "more packages is better".
